# GLOSSARY

Terms as used by Ìlànà, aligned with SEN102/212 and the standards it cites.

**Acceptance testing.** Testing performed by clients, end users, or business stakeholders to
decide whether the system satisfies business requirements and is ready for deployment.
Includes User Acceptance Testing, Alpha testing (at the developer site) and Beta testing
(by real users in a real environment).

**Architecture design.** The overall structure of a system and how that structure gives the
system conceptual integrity. The first of three design levels.

**Audit.** An examination of whether the team is following required standards, procedures and
policies. Conducted by independent personnel. Distinct from a review, which examines technical
content rather than compliance.

**BPMN.** Business Process Model and Notation. A standardised notation for modelling business
processes, with extensive swimlane support and strong process automation support.

**Build management.** Converting source code into executable software: compilation, linking,
dependency management, packaging, testing.

**CASE tools.** Computer Aided Software Engineering tools. Divided into Upper CASE (planning,
analysis, design), Lower CASE (coding, testing, maintenance) and Integrated CASE (whole
lifecycle). All share a central repository that also serves as a data dictionary.

**Change management.** Systematic handling of change requests: submission, impact analysis,
approval or rejection, implementation, testing, documentation.

**CMMI.** Capability Maturity Model Integration. A five-level maturity framework:
1 Initial, 2 Managed, 3 Defined, 4 Quantitatively Managed, 5 Optimizing.

**Correctness.** The software does exactly what the requirements say it should do.

**Cost variance.** A project metric: the difference between planned budget and actual
expenditure. Actual above planned is a negative variance (over budget).

**Defect density.** A product metric: confirmed defects divided by size, conventionally
defects per thousand lines of code (KLOC).

**Defect life cycle.** New -> Assigned -> Open -> Fixed -> Retest -> Verified -> Closed, with
the alternative states Reopened, Deferred and Rejected.

**Detailed design.** The third design level. Each module is examined to determine its data
structures and algorithms, recorded in a module specification document.

**DevOps.** An approach integrating development and operations into one process, characterised
by continuous integration, continuous deployment and automation.

**Domain requirement.** A requirement derived from the industry or field of use: specialised
rules, norms and regulatory policies the system must operate within.

**Efficiency.** How well the software uses system resources such as memory, processor and
storage.

**Elicitation.** The first stage of requirements engineering: identifying requirements from
the people involved, via interviews, questionnaires, workshops, brainstorming, observation,
document analysis, use cases and scenarios, and prototyping.

**Functional requirement.** What the system must do: the functions, features, inputs,
activities and outputs.

**Gate.** In Ìlànà: a named checkpoint between phases with explicit entry criteria, exit
criteria and required evidence.

**High-level design.** The second design level. Breaks the architecture into subsystems and
modules and shows how they interact.

**Inspection.** A highly structured review with defined roles (Moderator, Reader, Recorder)
and strict procedures, aimed at detecting defects early.

**Integration testing.** Testing combined modules to verify interfaces, data flow and
communication between components. Strategies: top-down, bottom-up, big bang.

**ISO/IEC 12207.** International standard defining software life cycle processes, grouped
into primary, supporting and organizational processes.

**Kanban.** An Agile method emphasising visual workflow management and Work-in-Progress limits
rather than fixed-length iterations. Items move To Do -> In Progress -> Done.

**Maintainability.** How easily the software can be modified, updated or corrected after
deployment.

**Non-functional requirement.** How the system performs its functions: performance, usability,
reliability, security, scalability.

**Plan-driven approach.** A development method where requirements, design, processes and
documentation are fully specified in advance and development proceeds under strict control.
Used for government and safety-critical systems.

**Portability.** The ability to run on different platforms or environments with minimal change.

**Process cycle time.** A process metric: elapsed time from the start of a task to its
completion.

**Process metric.** A measurement of the efficiency of development activities: defect rate,
time to fix defects, process cycle time.

**Process modeling.** Representing a process using diagrams, charts or formal notations to
describe activities, tasks, decisions, workflows and interactions.

**Product metric.** A measurement of the software artifact itself: lines of code, complexity,
defect density.

**Project metric.** A measurement of overall project performance: cost variance, schedule
adherence.

**Reliability.** How consistently the software performs without failure under normal conditions.

**Release management.** Planning, scheduling and controlling releases: planning, build
preparation, testing, deployment, monitoring, maintenance. Release types: major, minor,
patch, emergency.

**Requirements engineering.** The systematic process of identifying, documenting and managing
requirements: elicitation, analysis, specification, validation, management.

**Review.** Systematic examination of artifacts such as requirements documents, design
specifications and source code, before execution, to detect defects early. Forms: peer review,
walkthrough, inspection.

**Schedule adherence.** A project metric: how closely actual completion matches planned
completion. Planned 10 days, completed in 10 days, is high schedule adherence.

**Scrum.** An Agile method organising work into fixed-length sprints of typically two to four
weeks, with the roles Product Owner, Scrum Master and Development Team, and the events Sprint
Planning, Daily Scrum, Sprint Review and Sprint Retrospective.

**Security.** Protection of software and data from unauthorised access, attack or damage.

**SCM.** Software Configuration Management. Systematic control of changes to software
artifacts throughout the lifecycle: version control, change management, build management,
release management.

**SPI.** Software Process Improvement. Identify weaknesses, introduce improvements, monitor
impact. Cycle: Measure -> Analyze -> Improve -> Repeat.

**SQA.** Software Quality Assurance. A systematic set of activities ensuring that both the
process and the product meet requirements, standards and user expectations. Process-oriented
and prevention-focused, in contrast with testing, which is detection-focused.

**System testing.** Testing the complete integrated system against specified requirements.
Includes functional, performance, security, usability and stress testing.

**Test plan.** The document produced by test planning, covering objectives, scope, features to
be tested, strategy, environment, roles and responsibilities, risk analysis, schedule,
deliverables and exit criteria.

**Traceability.** Documented relationships among requirements, design, implementation, testing
and maintenance artifacts.

**UML activity diagram.** A flowchart-like UML notation showing flow of control among
activities, with start node, action nodes, control flow, decision, fork, join, merge, signal
send and receipt, note, and final flow node.

**Unit testing.** Testing the smallest components (functions, methods, classes, modules)
independently, usually by developers, usually automated.

**Usability.** How easy the software is for users to learn and operate.

**Validation.** Confirming that the specified requirements still reflect what users need and
that the system meets them. "Are we building the right thing?"

**Verification.** Confirming that the artifact conforms to its specification. "Are we building
the thing right?"

**Version control system.** A system that records changes to files over time. Centralized
(for example SVN) or distributed (for example Git).

**Walkthrough.** An informal review led by the author of the document or source code, who
presents the artifact to peers to explain its logic and gather early feedback.
