# PHASE 09 CHECKLIST

## Models
- [ ] The process that actually happens is modelled, not the idealised version
- [ ] Notation chosen appropriately: activity diagram for software flow, BPMN for cross-role business process
- [ ] Start node, activities, control flow, decisions and final node all present
- [ ] Decision conditions are labelled
- [ ] Parallelism uses fork and join, not implied concurrency
- [ ] Diagram is simple enough to read without a legend
- [ ] Model connects to requirements (traceability)

## Documentation coverage
- [ ] Requirements documentation exists
- [ ] Design documentation exists
- [ ] Technical documentation exists (source, API, configuration)
- [ ] User documentation exists
- [ ] Testing documentation exists

## Documentation quality
- [ ] Accurate: reflects the actual system, not an earlier version
- [ ] Complete: nothing essential missing
- [ ] Clear: understandable by its stated audience
- [ ] Consistent: uniform terminology and formatting
- [ ] Maintainable: easy to update
- [ ] Accessible: stakeholders can actually find it

## Standards
- [ ] A documentation standard is named (IEEE 830, 1016, 829, ISO/IEC 12207, or organisational)
- [ ] Documents follow the named structure
- [ ] Documentation is under version control

## Workflows
- [ ] Activities, roles, inputs, outputs and decision points are all specified
- [ ] Every decision point has its alternative paths defined
- [ ] Handoffs between roles are explicit
- [ ] The workflow matches how work actually moves

## The onboarding test
- [ ] A new engineer could set up, build, test and deploy this system from documentation alone
- [ ] That claim has been tested on a real newcomer (RIGOUR 3+)
